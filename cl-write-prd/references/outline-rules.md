# 动态大纲规则

## 基本原则

- 根据当前会话中最终确认的本次变化生成大纲，先按 `prd-style.md` 的“信息放置”为每项信息确定主要定义位置，再安排章节。
- 目标文档只有标题，且用户未指定章节或既有大纲时，先在对话中给出建议大纲。
- 用户已经提供大纲时优先遵循用户大纲。
- 不为了形式完整而增加无业务内容的章节。
- 简短规则并入最贴近的模块；沿用能力只提供理解变化所需的上下文，不按素材种类或每个技术细节增加小节。
- 实现方案先安排讲清本次核心决策的流程图，再按需补充差异表、页面或接入变化；图示范围及省略条件见 `prd-style.md`。

## 常见组合

- 普通功能通常围绕背景、实现方案和验收标准组织；存在页面交互变化时再展开页面设计。
- 涉及模型调用时，按需增加 Prompt 来源与必要接入说明；附件入口可以集中呈现，不要求每份附件各建一个摘要小节。
- 简单组件或局部交互调整可以直接组织为需求说明、必要页面材料和验收标准。

以上是组合示例。数据规则、权限、异常或技术说明只有在承担尚未表达的关键逻辑时才单列；章节各自提供新信息。

## 确认规则

- 用户说“开始写需求文档”且目标文档只有标题时，先输出建议大纲。
- 用户说“先写背景”等明确章节指令时，该指令即为对应章节的写入授权，直接编写，不重复确认，也不要求先完成整份大纲。
- 用户说“先在对话中输出”或“确认后再修改”时，先展示拟写内容并等待确认。
- 用户说“直接写”或“直接修改”时，在明确范围内跳过大纲和内容预览。
- 修改已有正文但替换或删除范围不明确时，先列出变更范围并等待确认。
