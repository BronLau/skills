# 产品需求文档风格

## 内容取舍

- 默认面向快速迭代，让未参与讨论的读者先看懂改什么、如何决策及怎样验收。先确定本次新增、改变和删除的行为，再组织章节；沿用能力只保留理解变化必需的上下文。
- 以实现和验收的判断需要决定详略：某项信息只有在省略后会改变对本次行为、关键条件或结果的理解，且其他位置尚未讲清时，才需展开。会话讨论篇幅、来源材料长度和“与需求有关”都不决定正文篇幅。
- 每项规则选择一个主要定义位置；其他位置只在阅读确有需要时给出简短引用。没有新增信息或定位作用的段落直接合并或删除，不为摘要、流程、模式说明和验收各写一遍。
- 将批注与纠正合并为最终方案。撤回的原型尝试从方案中移除，不转写为“不展示”“不支持”等排除清单；线上已有能力的删除、改变或关键约束，仍写清变化与生效条件。
- 会话中的技术讨论、自检建议和本地验证用于核对需求，不自动成为需求。测试命令与环境、临时测试数据、验证截图、通过/失败或尚未验证的状态、排查修复过程等记录留在对话中，不作为正文、图表或附件写入 PRD。用于展示已确认页面与交互的原型截图仍按页面设计规则插入。
- 决定本次行为的条件、数值、异常分支和已确认产品约束在主要定义位置准确保留。验证发现的问题，只提炼用户最终确认的产品变化；临时环境问题不转为产品限制，尚未确认且会改变方案的问题在对话中提出。
- 用户明确要求详细方案、技术设计、完整 Prompt、测试用例或验证报告时，按其要求展开对应部分。

## 信息放置

按信息用途选择载体，不要求每份文档配齐所有类型。图表也是正文的一部分，单元格使用短句或关键词；把长段落搬进表格不减少阅读负担。

| 信息 | 主要呈现位置 |
| --- | --- |
| 核心决策、条件分支、重试与回退 | 流程图；正文只补充图中尚未表达的必要条件与例外 |
| 模式差异、字段或参数对照 | 按相同维度组织的精简表格，表后不再复述各行 |
| 页面样式与交互 | 原型和截图；文字说明未能由画面表达的行为变化 |
| 影响程序实现的接入变化 | 集中的简短接入表或必要文字，如新格式解析、时间含义、素材绑定及历史兼容 |
| 模型执行细则、完整 Prompt、长结构示例 | 已确认且可访问的完整来源或附件；正文标明用途、本次变化和入口 |

正文应足以理解本次产品行为和研发改动，附件提供执行细节。必要的程序改动不能只埋在 Prompt 中；沿用协议和模型执行细则也不因提供了附件而再摘要一遍。

## 文档开头

- 在文档标题下、首个一级章节前，用一段需求摘要概括本次建设的核心变化和业务结果。
- 需求摘要固定使用飞书引用块；使用 XML 编辑时写为 `<blockquote>...</blockquote>`。

## 标题与层级

- 一级章节使用中文序号，如“一、背景”“二、实现方案”。
- 实现方案中的内容分组使用三级标题，如“业务流程”“页面设计”。
- 页面设计项使用带阿拉伯数字的四级标题，如“1. 资产页”。
- 独立章节和独立页面设计项之间使用分割线。
- 是否出现 Prompt、数据规则或验收标准等章节，由当前需求决定。

## 背景

- 用一个简短段落说明问题与目标，长度由需求复杂度决定。
- 按“当前缺口 → 造成的问题 → 本次建设目标”组织。
- 不拆分市场分析、产品价值等无必要小节。
- 不使用营销化或宽泛表达。

## 业务流程

- 优先用流程图讲清本次变化涉及的核心决策，让读者沿图看出触发条件、分支和结果。沿用的上下游只用于定位；总览中的概括节点如包含本次关键逻辑，应展开或连接局部详图。
- 只有逻辑确实简单，少量文字或一张小表即可完整讲清，且没有多阶段依赖或交织分支时，才可省略流程图。
- 图中路径与条件由 [diagram-design.md](diagram-design.md) 指导绘制，保留原生编辑能力；补充内容按“信息放置”安排，不另写一份与图对应的完整步骤说明。

## 页面设计

在“页面设计”标题下、首个页面子标题前放置本次已确认的 HTML 原型附件，使用飞书文件卡片视图。同一份原型只保留一张当前版本卡片。

每个页面或关键交互依次呈现四级标题、原型截图、居中灰色的中文引号图名及分割线。无法截图或用户选择手动配图时，使用黄色“截图内容描述”占位。图名后按需补充无序列表，无须为每张图配齐说明。

- 布局、宽度、颜色、透明度等纯视觉样式交给原型和截图；确实影响功能或用户明确要求时再展开。
- 默认值、显示条件、状态变化及影响操作结果的规则仍需文字定义，不能从截图当前状态推断。已经在其他模块定义的规则直接引用。
- 图后说明只补充新增、变化或容易误解的行为；现有交互按“内容取舍”处理。

## 字段与规则

- 仅列会改变本次实现或联调结果的新增、变更字段，说明用途、归属及必要默认值；沿用协议引用已有定义，多个字段确需对照时使用表格。
- 控件名称使用中文引号。
- 积分、数量、文件类型、大小限制和状态值使用准确数字。
- 在主要定义位置写清触发条件、系统行为和结果；图表已表达的部分不再补成一段完整文字。

## Prompt

- 仅在涉及模型或 Prompt 时设置对应内容，按具体模型任务组织，不强制固定结构；多阶段关系确需图示时，同样按 `diagram-design.md` 绘制原生画板。
- 已有完整 Prompt 时，复用已确认且读者可访问的来源或附件，同一内容不提供多格式重复副本；正文摘要明确标注，不替代完整原文。
- 正文只说明任务职责、本次影响业务结果的变化及必要输入输出。变化已在实现方案讲明时，此处仅保留用途和完整来源入口；模型执行步骤、格式细则和长结构示例由完整 Prompt 承载。
- 按实际调用区分 System Prompt、动态 User 模板和素材输入。程序接入只展开本次需修改的组装、解析、校验、素材绑定或兼容边界，按“信息放置”集中定义，不混入发送给模型的指令。

## 验收标准

- 按实现方案中的能力模块设置三级子标题，模块名称优先沿用页面、流程或核心能力名称；即使只有一个模块，也保留子标题。
- 各组使用飞书待办复选框，每项围绕一个可独立判断的业务结果，只保留必要前置条件与预期结果。同一结果的关联条件合并，结果不同且可能独立失败的能力分项验证。
- 已定义的分支、参数和例外引用对应规则或表格，保留核对目标，不抄写字段清单与实现步骤。引用覆盖全部适用分支；篇幅压缩不减少主链路与决定性分支的覆盖。
- 验收描述应达到的产品结果，不带入本地验证的执行结论或通过状态；顺序与实现方案基本一致，不按每个技术小节重复建组。
- 只有影响核心结果的交互或异常才单列；纯视觉样式由原型承接，用户明确要求时再增加专项验收。

## 成稿检查

写入前检查内容，写入后核对实际结果。先完成取舍与去重，再处理排版：

- **变化与决策：** 核心改动容易找到，图能讲清本次关键判断，而非只展示系统调用链；简单需求的短文或表格同样能明确条件与结果。
- **新增信息：** 逐段核对是否提供了尚未表达的决策、约束或必要索引；没有则删除、合并或改成简短引用。连续补充说明归并为最终规则，保留影响结果的例外。
- **信息分工：** 模式表后、Prompt 摘要和验收未重新展开同一套规则；必要接入变化可直接找到，模型执行细则由完整附件承载。
- **完整性：** 决定性条件、准确数值与必要分支仍可定位，引用有效，完整来源可访问；按信息价值精简，不用固定字数或条目上限裁掉需求。

## 语言

- 使用简洁、确定、客观的产品语言。
- 优先使用“用户可……”“系统……”“点击后……”等句式。
- 已确认需求使用确定表述，尚未确认的产品约束按“内容取舍”处理。
- 同一对象全文使用统一名称。
- 只记录最终方案，不记录讨论过程。
- 段落、列表项和待办项优先删除标题、章节或前文已经明确的重复主语和背景，只保留当前规则需要判断的信息。
- 尾行仅剩 4 个以内字符或一个短词时，在不丢失触发条件、系统行为和业务结果的前提下重写整句，并比当前溢出长度多精简几个字，为不同显示宽度留出余量。
- 通过精简措辞优化换行，不插入空格或手动换行，不缩小字号。
