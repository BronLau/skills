# 产品需求文档风格

## 内容取舍

- 默认面向快速迭代，正文让研发看清本次改什么、主流程如何运行、关键规则和预期结果。
- 逐条判断：删掉这段内容，是否会让团队对本次改动、主流程或关键规则产生不同理解？保留消除这些歧义所需的信息，其余合并或省略；会话讨论得细不代表正文也需要同等展开。
- 边界与异常仅在直接影响核心流程或关键业务结果时说明。常规失败、兼容和恢复沿用现有机制，必要时用一句话交代；尚未确认且会改变方案的问题在对话中提出。
- 同一规则在最贴近的模块说明一次。流程写主链路，页面写新增或变化的交互，验收检查业务结果；各部分各尽其用。
- 用户针对本次文档明确要求详细方案、技术设计、完整 Prompt 或测试用例时，再展开对应部分。

## 文档开头

- 在文档标题下、首个一级章节前，用一段需求摘要概括本次建设的核心变化和业务结果。
- 需求摘要固定使用飞书引用块；使用 XML 编辑时写为 `<blockquote>...</blockquote>`。

## 标题与层级

- 一级章节使用中文序号，如“一、背景”“二、实现方案”。
- 实现方案中的内容分组使用三级标题，如“业务流程”“页面设计”。
- 页面设计项使用带阿拉伯数字的四级标题，如“1. 资产页”。
- 独立章节和独立页面设计项之间使用分割线。
- 是否出现 Prompt、数据规则或验收标准等章节，由当前需求决定。

## 背景

- 用一个简短段落说明问题与目标，长度由需求复杂度决定。
- 按“当前缺口 → 造成的问题 → 本次建设目标”组织。
- 不拆分市场分析、产品价值等无必要小节。
- 不使用营销化或宽泛表达。

## 业务流程

- 使用飞书画板原生节点表达主流程。
- 图下使用加粗的“步骤说明：”。
- 使用有序列表说明流程步骤。
- 每一步使用“加粗动作名称：具体说明”。
- 步骤聚焦用户动作、系统处理和最终结果。

## 页面设计

在“页面设计”标题下、首个页面子标题前放置本次已确认的 HTML 原型附件，使用飞书文件卡片视图。同一份原型只保留一张当前版本卡片。

每个页面或关键交互依次包含：

1. 四级标题；
2. 自动获取的原型截图，无法完成或用户选择手动配图时使用黄色“截图内容描述”占位；
3. 使用中文引号标注、居中且为灰色的截图名称；
4. 无序列表形式的交互和业务规则；
5. 分割线。

说明只覆盖新增、变化或容易误解的交互。普通关闭、常规输入、滚动等基础操作不单独说明。

## 字段与规则

- 仅列影响核心规则或联调对齐的新增、变更字段，说明用途、归属及必要默认值；多个字段确需对照时使用表格。
- 控件名称使用中文引号。
- 积分、数量、文件类型、大小限制和状态值使用准确数字。
- 每条规则写清触发条件、系统行为和结果。

## Prompt

- 仅在功能确实涉及模型或 Prompt 时增加对应章节。
- 使用具体模型任务名称作为小标题。
- 有组装逻辑或多阶段处理时，可使用飞书画板表达。
- 修改既有 Prompt 时，说明任务目标、必要输入输出和关键指令变化；代码标识与片段以研发能定位和理解改动为准。
- 不强制拆分为输入参数、后端组装规则、有参考图或无参考图等固定结构。

## 验收标准

- 按实现方案中的能力模块设置三级子标题，模块名称优先沿用页面、流程或核心能力名称；即使只有一个模块，也保留子标题。
- 每个子标题下使用飞书待办复选框，提炼能判断核心功能是否达成的业务结果，覆盖主链路与决定性分支。
- 每项对应一项可以独立判断通过或失败的核心能力。
- 同一业务链路的关联条件可以合并在一项中。
- 沿用核心业务模块组织验收，可合并前文的技术小节；顺序与实现方案和页面设计基本一致。
- 跨模块的端到端结果仅在确有必要时单独成组，不重复各模块已经覆盖的验收内容。
- 验收项保持结果导向，只有影响核心结果的交互或异常才单列；常规交互和字段细节由实现方案承接。

## 语言

- 使用简洁、确定、客观的产品语言。
- 优先使用“用户可……”“系统……”“点击后……”等句式。
- 避免“建议”“大概”“可能”“预计”等不确定表达。
- 同一对象全文使用统一名称。
- 只记录最终方案，不记录讨论过程。
- 段落、列表项和待办项优先删除标题、章节或前文已经明确的重复主语和背景，只保留当前规则需要判断的信息。
- 尾行仅剩 4 个以内字符或一个短词时，在不丢失触发条件、系统行为和业务结果的前提下重写整句，并比当前溢出长度多精简几个字，为不同显示宽度留出余量。
- 待办项包含多个可独立验收的能力时拆分；属于同一结果的关联条件保持合并并压缩表达。
- 通过精简措辞优化换行，不插入空格或手动换行，不缩小字号。
