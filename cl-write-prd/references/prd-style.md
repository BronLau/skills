# 产品需求文档风格

## 内容取舍

- 默认面向快速迭代，让未参与讨论的读者看清本次变化、关键规则与预期结果。正文定义业务行为，原型表达视觉呈现，附件承载完整细节。
- 以会话中已核实的现状为基准，重点写新增与变化。沿用能力只交代与本次需求的关系；理解新流程所必需的行为可简述，不重新编写操作手册。
- 结合原型、附件及已有规则判断：删掉这段是否会造成不同理解？正文只保留消除歧义所需的信息，会话讨论的篇幅不决定文档详略。
- 同一规则在最贴近的模块完整定义一次，其他位置明确引用。图、表、文字互补；摘要概括变化，流程串联主链路，页面补充交互，验收检查结果，不各自重写整套规则。
- 将批注与纠正合并为最终方案。撤回的原型尝试从方案中移除，不转写为“不展示”“不支持”等排除清单；线上已有能力的删除、改变或关键约束，仍写清变化与生效条件。
- 关键条件、准确数值和必要接口约定应完整保留。边界、异常及已知限制仅在影响核心结果或交付判断时简述；待验证事项标明状态，不展开测试历史。尚未确认且会改变方案的问题在对话中提出。
- 用户明确要求详细方案、技术设计、完整 Prompt 或测试用例时，按其要求展开对应部分。

## 文档开头

- 在文档标题下、首个一级章节前，用一段需求摘要概括本次建设的核心变化和业务结果。
- 需求摘要固定使用飞书引用块；使用 XML 编辑时写为 `<blockquote>...</blockquote>`。

## 标题与层级

- 一级章节使用中文序号，如“一、背景”“二、实现方案”。
- 实现方案中的内容分组使用三级标题，如“业务流程”“页面设计”。
- 页面设计项使用带阿拉伯数字的四级标题，如“1. 资产页”。
- 独立章节和独立页面设计项之间使用分割线。
- 是否出现 Prompt、数据规则或验收标准等章节，由当前需求决定。

## 背景

- 用一个简短段落说明问题与目标，长度由需求复杂度决定。
- 按“当前缺口 → 造成的问题 → 本次建设目标”组织。
- 不拆分市场分析、产品价值等无必要小节。
- 不使用营销化或宽泛表达。

## 业务流程

- 实现方案的核心逻辑优先使用流程图，先呈现从触发到结果的主链路、关键判断及分支关系。较长的处理链路、多阶段依赖或交织分支应画流程图，不用纯文字或规则表替代。
- 只有逻辑确实简单，少量文字或一张小表即可完整讲清，且没有多阶段依赖或交织分支时，才可省略流程图。
- 流程图使用飞书画板原生节点，节点聚焦动作、关键条件和结果；字段、枚举、参数及细分条件由表格或正文补充。
- 流程图使用独立于阅读器主题的配色：默认采用不透明浅色背景、浅色节点和深色文字；背景覆盖全部节点、外绕连线、箭头及标签的范围并留出边距。所有文字均显式配色，不继承作者当前的深色或浅色模式；深色强调节点使用白字时，须同时固定其深色背景。
- 连线与箭头默认使用固定深灰色 `#646A73` 和 100% 不透明度，线宽与箭头大小以文档实际显示比例下清晰可辨为准；主路径和侧边返回路径保持同等可读性。
- 连线标签默认使用深色文字 `#1F2329` 与不透明白底 `#FFFFFF`，遮住穿过文字的线条和底纹；文字与背景成对设置。配色从首次生成时落实，写入与校验按 `lark-editing.md` 执行。
- 图、表已经讲清的内容不逐条复述，文字仅补充尚未表达的关键行为。
- 需要步骤说明时，以加粗的“步骤说明：”开头，使用有序列表，按“加粗动作名称：具体说明”表达。

## 页面设计

在“页面设计”标题下、首个页面子标题前放置本次已确认的 HTML 原型附件，使用飞书文件卡片视图。同一份原型只保留一张当前版本卡片。

每个页面或关键交互依次呈现四级标题、原型截图、居中灰色的中文引号图名及分割线。无法截图或用户选择手动配图时，使用黄色“截图内容描述”占位。图名后按需补充无序列表，无须为每张图配齐说明。

- 布局、宽度、颜色、透明度等纯视觉样式交给原型和截图；确实影响功能或用户明确要求时再展开。
- 默认值、显示条件、状态变化及影响操作结果的规则仍需文字定义，不能从截图当前状态推断。已经在其他模块定义的规则直接引用。
- 图后说明只补充新增、变化或容易误解的行为；现有交互按“内容取舍”处理。

## 字段与规则

- 仅列影响核心规则或联调对齐的新增、变更字段，说明用途、归属及必要默认值；多个字段确需对照时使用表格。
- 控件名称使用中文引号。
- 积分、数量、文件类型、大小限制和状态值使用准确数字。
- 每条规则写清触发条件、系统行为和结果。

## Prompt

- 仅在涉及模型或 Prompt 时设置对应内容，按具体模型任务组织，不强制固定结构；多阶段关系确需图示时可使用飞书画板。
- 已有完整 Prompt 时，复用已确认且读者可访问的来源或附件，同一内容不提供多格式重复副本；正文摘要明确标注，不替代完整原文。
- 正文提炼任务目标、关键变化及必要输入输出，已有业务规则直接引用。完整来源已覆盖的判定细则和输出结构不在正文复述，代码标识与片段以研发能定位和理解改动为准。
- 按实际调用明确 System Prompt、动态 User 模板和素材输入的用途。程序侧参数、校验、坐标换算及后处理归入对应实现规则，集中定义必要接入约定，不混入发送给模型的指令。

## 验收标准

- 按实现方案中的能力模块设置三级子标题，模块名称优先沿用页面、流程或核心能力名称；即使只有一个模块，也保留子标题。
- 各组使用飞书待办复选框，验证主链路与决定性分支的业务结果；顺序与实现方案基本一致，可合并技术小节。
- 已在前文定义的分支、参数或处理规则，明确引用对应表格或规则，不复制实现说明。引用后仍须逐一验证所有适用分支，不能省略覆盖。
- 每项能独立判断通过或失败；同一结果的关联条件合并，不同核心能力分开。跨模块结果仅在确有必要时单列，避免重复覆盖。
- 只有影响核心结果的交互或异常才单列；纯视觉样式由原型承接，用户明确要求时再增加专项验收。

## 语言

- 使用简洁、确定、客观的产品语言。
- 优先使用“用户可……”“系统……”“点击后……”等句式。
- 已确认需求使用确定表述，待验证限制明确标注。
- 同一对象全文使用统一名称。
- 只记录最终方案，不记录讨论过程。
- 段落、列表项和待办项优先删除标题、章节或前文已经明确的重复主语和背景，只保留当前规则需要判断的信息。
- 尾行仅剩 4 个以内字符或一个短词时，在不丢失触发条件、系统行为和业务结果的前提下重写整句，并比当前溢出长度多精简几个字，为不同显示宽度留出余量。
- 通过精简措辞优化换行，不插入空格或手动换行，不缩小字号。
