# 创量需求文档编写

承接当前会话已经完成的原型设计，将最终确认的产品需求整理并写入用户提供的飞书文档。不要重新设计原型，也不要要求用户重复已经在当前会话确认的信息。

默认面向高速迭代中的研发对齐，正文聚焦本次业务变化和关键规则，原型表达视觉呈现，附件承载完整细节；内容取舍统一按 `prd-style.md` 执行。

## 前置能力

- 操作飞书文档前，阅读并使用当前 `lark-doc` Skill；认证、身份或权限问题按其路由使用 `lark-shared`。
- 自动截图前，确认当前会话具备浏览器操作与截图保存能力，并遵循对应工具或已安装 Skill 的指引。
- 需要业务流程图时，完整阅读并使用 `lark-whiteboard` Skill；使用飞书画板原生节点，不使用 SVG。

## 信息优先级

按以下顺序确定需求事实：

1. 当前会话中用户最新确认的要求。
2. 当前会话中已经呈现并由用户确认的原型最终状态，包括浏览器评论、截图证据和交互决策。
3. 当前会话中较早的设计要求。
4. 用户提供的 PDF、Prompt、接口数据和其他资料。
5. 目标飞书文档中已经存在的内容。

同一事项出现冲突时采用最新指令。先将纠正合并为最终方案，再按 `prd-style.md` 提取本次需要实现的行为，不逐条转述纠正过程。需要页面截图时，可打开原型并复现已确认的交互状态；若实际页面与最终需求不一致，说明差异并保留占位。

## 参考文件路由

- 开始写作前读取 [style-source.md](references/style-source.md) 与 [prd-style.md](references/prd-style.md)。
- 目标文档只有标题或需要调整大纲时读取 [outline-rules.md](references/outline-rules.md)。
- 编写页面设计或补充截图时读取 [screenshot-placeholder.md](references/screenshot-placeholder.md)，完成自动截图、插图或降级占位。
- 读取、写入和校验飞书文档时读取 [lark-editing.md](references/lark-editing.md)。

## 工作流程

### 1. 汇总当前会话

以会话中已核实的现状为基准，从最终确认方案中提取：

- 本次要解决的问题与建设目标；
- 用户主操作路径及新增、变化的交互；
- 决定核心行为的业务规则，以及必要的数据、模型或 Prompt 改动；
- 可判断核心能力是否达成的验收结果。

按 `prd-style.md` 提炼本次变化。会话中的技术讨论、自检建议不自动转为需求；影响交付判断的已知限制或未完成验证，在对应规则旁简述。信息不足会实质改变核心方案时再向用户确认。

### 2. 读取风格范本

读取 `style-source.md` 指定的范本文档最新版本，提取标题层级、编号方式、语言风格、核心逻辑的表达方式及飞书组件用法。内容详略按本次需求决定，不照搬范本的篇幅或细节密度，也不复制其具体业务结构。

范本文档无法访问时，以 `prd-style.md` 为兜底。范本文档或 `lark-doc` 通用样式与 `prd-style.md` 冲突时，以本 Skill 的 PRD 专属风格规则为准。

### 3. 读取目标文档

读取用户提供的飞书文档最新版本。已有正文时，确认本次修改范围和相关规则的已有定义位置，保留范围外内容，按 `lark-editing.md` 保护媒体资源与富文本结构。

### 4. 设计大纲

根据当前需求动态选择章节，不强制所有文档包含相同大纲。实现方案的核心逻辑优先用流程图，省略条件按 `prd-style.md` 判断；页面设计、数据规则、Prompt 或验收标准按当前功能组织。

目标文档只有标题，且用户只笼统要求“开始写需求文档”时，先在对话中给出建议大纲并等待确认。用户明确要求直接编写，或明确指定当前章节时，该指令本身即构成对应范围的写入授权，直接进入该章节。

### 5. 分阶段编写

只编写用户当前要求的部分：

- “先写背景”只写背景；
- “开始写业务流程”按 `prd-style.md` 的流程图优先原则表达核心逻辑；
- “开始写页面交互”同步 HTML 原型附件，编写页面设计与交互说明，并自动截图；无法完成截图插入时保留占位；
- “开始写 Prompt”根据实际模型任务决定内容结构；
- “开始写验收标准”先按实现方案中的能力模块创建子标题，再在各模块下使用飞书待办复选框。

更新已有内容时，在授权范围内将相关模块整理为最终方案，合并重复定义并清理过期说明；已有规则可直接引用，不逐条追加会话批注。不要提前生成用户尚未要求的后续章节。

### 6. 同步原型与页面截图

先按 `lark-editing.md` 将本次已确认的 HTML 原型作为文件卡片放在“页面设计”标题下、首个页面子标题前；附件与截图使用同一版本。

默认按 `screenshot-placeholder.md` 操作已确认的原型，复现目标状态、截取关键区域并检查图片，再通过飞书文档接口插入对应章节。用户授权写入页面设计或补充截图时，包含该范围所需的原型附件同步、取证与图片写入；用户要求先预览或手动配图时按其要求执行。

浏览器未接入、目标状态无法复现或图片插入失败时，按该参考降级为黄色“截图内容描述”，在汇报中说明具体原因。图片下方保留居中灰色的截图名称，交互说明保持正文样式。

### 7. 写入飞书

按以下规则判断是否需要写入前确认：

- 用户只提供文档并笼统要求开始编写，且目标文档只有标题时，先展示建议大纲并等待确认；
- 用户明确要求编写某个章节时，该指令即为写入授权，直接进行块级编辑，不重复确认；
- 用户明确要求“先在对话中输出”或“确认后再修改”时，先展示拟写内容并等待确认；
- 修改已有正文但替换或删除范围不明确时，先列出拟新增、替换或删除的内容并等待确认；
- 用户明确说“直接写”“直接修改”时，在其授权范围内跳过预览。

禁止整篇覆盖已有文档，禁止删除范围外内容。

### 8. 写入后校验

重新读取修改后的章节完成结构和内容校验，再按 `lark-editing.md` 在飞书可见页面检查本次写入范围的实际排版。一次处理范围内发现的全部短尾行。

- 文档开头的需求摘要是否使用飞书引用块；
- 标题层级、编号和分割线是否符合范本；
- HTML 原型是否以文件卡片放在“页面设计”标题下、首个页面子标题前，并与截图版本一致；
- 本次变化是否清楚，规则是否集中定义，关键条件、决定性分支及影响交付的已知限制是否保留；
- 实现方案是否用流程图串起核心链路与关键分支，省略流程图时是否确属简单逻辑；包括连线标签在内的文字与背景是否按 `prd-style.md` 配色并通过画板校验；
- 页面、控件、字段和业务对象名称是否统一；
- 枚举、积分、数量、文件限制和状态是否准确；
- 段落、列表项和待办项的尾行是否仅剩 4 个以内字符或一个短词；有则改写整句并留出余量；
- 截图是否对应已确认的页面状态，取景是否完整清晰且没有无关边缘留白，图片是否实际插入正确章节，截图名称是否居中并使用灰色文字；降级占位是否使用黄色文字并足以复现，原因是否已说明；
- Prompt 摘要、完整来源与程序接入约定是否各自清楚且一致；
- 验收是否按能力模块组织，引用是否明确可定位，主链路与决定性分支是否可判断通过或失败。

## 硬性规则

- 按 `prd-style.md` 描述最终业务变化、必要行为及结果，不将原型迭代过程写入正文。
- 控件名称使用中文引号，字段和枚举使用准确值。
- 不固定需求文档大纲，不固定 Prompt 内部结构。
- 截图取自真实原型，图片插入成功以回读结果为准。
- 原型操作限于复现截图状态；修改原型代码或执行真实生成、提交等业务操作需有对应授权。
- 不覆盖整篇文档，不修改用户未授权的章节。
